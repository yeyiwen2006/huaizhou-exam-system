# 主备管理与单节点运行

## 运行原则

支持一个或两个受管节点，始终只有一个活动主节点。活动节点本机数据库、身份和资源健康时，另一台未部署、未启动或失联均不会单独阻断业务。数据库连接使用本机持久提交，业务成功仍经过权威节点、服务代次、资源和本机确认记录检查。对端可用时继续取得第二份独立持久确认；不可用时自动保留本机成功并后台重试，不需要进入“单机应急”。

服务器管理显示实际保护状态。只有数据库流复制、资源、证书和最新双侧独立确认都核实后显示“双节点保护正常”；否则清楚显示“单节点运行”或“状态未核实”。`HighAvailabilityStatus.EffectiveProtectionMode` 按当前证据给出有效状态，`SynchronousProtectionVerified` 是双份保护证明。`State.ProtectionMode` 保留旧持久格式；`EmergencySingleNode` 表示本机确认，不再代表必须人工授权。主节点自动降级不增加代次，也不改变活动节点。

## 方案 A：人工隔离后接管

管理服务独立于业务进程。业务可用时，考务登录后以现有业务令牌换取管理会话；业务不可用时，从登录页的“服务器管理 / 故障接管”进入，使用部署文件中已配置的主备管理连接，再以原考务账号独立登录。Windows 管理宿主在数据库无法读取时可使用此前已验证的本机加密账号缓存，未缓存的账号不能凭空获得权限。

服务器管理页统一显示主机和备机；点击节点行会填入“准备变为主服务器的节点”，备注可留空。目标经自身管理服务核实为备用节点时，才可发起“接管为主服务器”。操作确认仍须如实确认旧主已关机，或者已从全部业务网络隔离。隔离应覆盖校园网、Radmin 等虚拟局域网、公网反向代理入口及其他学生/考务访问路径，保持独立管理通道时也不得开放旧主业务。

本方案没有第三方仲裁，也不自动断电或配置交换机。失去心跳只触发重连和状态更新，永不自动提升。操作确认记录的是已经完成的现场隔离；代次也不能阻止仍与新主隔绝的旧主服务自己的旧客户端。

接管程序读取备机自身保存的独立确认，核对数据库已接收并重放的持久边界、非暂停恢复角色、集群、数据库、时间线、资源和解锁材料。旧主整机、磁盘或日志不可访问时不再要求读取旧主确认目录。可恢复范围以本机副本为准：旧主在复制中断后仅本机保存的新数据可能不在备机，不能声称零丢失。

通过后依次持久保存操作意图、停止本机备用业务进程、提升 PostgreSQL、递增服务代次、登记新活动节点并隔离旧角色、持久保存部署选择，再自动启动业务并等待就绪。学生端沿用原设备身份、答案、请求编号和交卷快照重连。操作中断或响应丢失时查询原请求，不能新建请求重复提升。

## HTTP 与 CLI

管理 HTTPS、账号、会话及权限规则继续生效。请求绑定逻辑服务器、本机节点、已认证操作者、预期代次和状态版本。

| 路径，前缀 /management/v1 | 用途 |
| --- | --- |
| GET /high-availability/status | 查询实际角色、保护状态和证据 |
| POST /high-availability/takeover | 当前本机备节点，必须附旧主隔离证据 |
| POST /high-availability/rebuild | 隔离中的本机旧节点或需要重新初始化的备机，必须确认保留旧目录后重建 |
| POST /high-availability/reprotect | 手工核对已恢复备用的兼容入口；自动补齐和业务成功不以此为前提 |
| GET /operations/{requestId} | 查询原持久操作及中断核对结果 |

图形界面只保留本次接管所需操作；重建、恢复同步保护、配置和备份恢复等运维入口继续由受控 API / CLI 提供。管理连接来自本机部署文件，页面不再提供手工切换或导入连接入口。节点表保留最新观察，过期或不可达以文字标注；过期显示值不得用于接管校验。

旧 `emergency` 路由及枚举用于识别历史日志；新请求返回无需单独启用单机应急，不提供 GUI 按钮。CLI 继续使用 management 命令组及原请求 JSON。已核实的单节点状态读取退出码为 0，状态未知或本机关键检查失败为 6，代次/版本冲突为 4。不能把“对端不可用”单独判为业务不可用。

请求字段为 `RequestId, ServerId, NodeId, ActorId, ExpectedEpoch, ExpectedVersion, TargetNodeId, Reason, Isolation, ConfirmDestructiveRebuild`。隔离操作者须等于会话操作者，隔离目标须是旧活动节点。Reason 对应可选备注，允许为空且至多 500 字符；请求身份、操作者、目标、代次和操作结果仍写入审计。内部执行计划仅存受保护日志，对外响应不返回连接串或证书配置。

## 复制恢复与旧主回归

未变更角色的备机恢复后继续 WAL 流复制。活动节点后台每轮约 3 秒尝试补齐版本化资源并刷新独立确认；临时失败继续重试，不阻塞本机业务。业务确认对单次对端确认最多等待约 750 毫秒，失败后暂避约 3 秒。本机 I/O、身份或资源核对失败仍不返回成功。

资源通过独立认证 HTTPS 端点传输：

| 端点，前缀 /replication/v1 | 方向和限制 |
| --- | --- |
| GET /authority | 查询受信节点的实际活动身份与代次，不授予提升权限 |
| GET、POST /resources | 活动节点向同集群、同代次的恢复中备用节点补齐完整资源快照 |
| GET /resources/source、/resources/snapshot | 隔离旧节点重建时从当前活动节点读取资源，禁止使用旧主资源作为源 |

资源快照只覆盖配置的版本化资源目录。数据库使用 WAL 和基础备份复制；节点私钥、实际连接配置和管理凭据由各节点部署保护，不通过资源端点复制。接收端限制压缩与展开大小、路径和条目数量，在独立暂存目录核对版本，重新核对备用身份后持久替换，保留原资源副本。接收与提升使用同一确认目录锁，接收端成为主节点后拒绝旧源覆盖。

后台维护复用已核验的资源摘要缓存。文件清单、元数据和目录变更通知保持一致时，不再每隔数秒重复读取并刷盘全部资源；发现变化则重新计算。对端摘要一致时跳过传输，需要补齐时仍在打包后复核源摘要，源文件在此期间改变会使本次复制失败并等待重试。资源摘要一致本身不代表双节点保护，数据库复制位置和独立确认仍须另行通过检查。

资源查询和上传由专用复制 HTTP 客户端处理，一次资源同步使用两分钟总期限，避免被其他请求使用的 30 秒客户端超时提前中断；请求和异步复制也遵守调用方的取消请求。接收端在每个完整文件写入结束时可靠刷盘，随后校验整个暂存目录摘要，避免对每个小数据块重复强制刷盘。同一快照因响应丢失而重传时，仍核对接收方身份；当前资源已经一致则不再次生成相同的历史副本。

已接管后恢复的旧主继续保持业务隔离，先停止旧业务，从当前活动节点创建新基础备份和资源快照，核对结果，保留旧数据库与旧资源为隔离原件，再启动新的备用库及确认监听。重建期间当前主节点保持业务可用。不得把旧数据库改个角色直接上线，不自动合并分叉数据，也不自动切回原主。

初始化和受控重建的基础备份使用持久物理复制槽；受控重建按节点和本次工作目录生成确定的槽名，并通过 `--write-recovery-conf` 写入新备用库的 `primary_slot_name`，使基础备份结束到备用库开始流复制之间仍保留所需 WAL。失败后不会自动删除复制槽、覆盖原工作目录或另建请求重复执行；须先查询原操作和核对材料归属。

基础数据传输使用 `--compress=server-gzip:level=1`，保留快速 checkpoint、流式 WAL、可靠落盘与完整核验；不使用 `--no-sync`。该优化不改变恢复边界，也不证明现场网络已经提速。参数说明见 [PostgreSQL 18 的 pg_basebackup 文档](https://www.postgresql.org/docs/18/app-pgbasebackup.html)。实际低磁盘、失效复制槽和缺失恢复材料仍须处理；[自动备份保留与磁盘告警](operations/automatic-backup-retention.md)说明了维护与清理条件。

旧业务进程发现同集群更高代次的可信活动节点时，保存 retired-epoch.json 并退出；同一旧代次重启仍被拒绝。此保护不能代替持续的现场隔离。管理重建采用新的受保护代次目录，旧记录保留。

## 部署配置

| 受保护键 | 要求 |
| --- | --- |
| HighAvailability:RequiredNodeIds | 一或两个不同节点，包含本机；与发布公钥和学生信任拓扑一致 |
| HighAvailability:BootstrapPrimary | 仅首台、第一代、空的新主数据库显式设 true；已有状态不修改，备库和已有业务数据拒绝初始化 |
| HighAvailability:Nodes:&lt;node&gt;:ConnectionString | 管理配置可有一个或两个不同数据库端点；不能把同一数据库伪装成双机 |
| 同节点 ResourcesDirectory、CertificateThumbprint、ConfirmationDirectory | 各自节点的资源、证书及独立确认根；远端资源通过 HTTPS 读取，不要求共享本地盘符 |
| 同节点 BusinessHttpsUrl | 正常 TLS 校验的 HTTPS 根地址，不含用户信息、路径或查询 |
| HighAvailability:SelectionPath | 受保护部署选择，管理可写、业务可读；未配置时位于 Management:OperationDirectory |
| HighAvailability:RebuildRoot | 独立非根暂存目录，不与数据库或资源目录互相包含 |
| HighAvailability:PostgresDataDirectory、PostgresConfigurationPath、PostgresServiceName | 固定本机数据目录、数据目录外受保护配置、受控 PostgreSQL 服务 |
| HighAvailability:WalArchiveDirectory、WalArchiveScriptsDirectory | 本机归档及预部署脚本目录，保持既有恢复保障 |
| Backup:PostgresBinDirectory | 与数据库版本匹配的 PostgreSQL 工具绝对目录 |
| Confirmation:Directory | 预建受保护本机确认目录，必须可可靠持久写入 |
| Confirmation:StandbyNodeId、StandbyHttpsUrl、PeerToken | 双机复制配置；只部署一台时可不配置对端地址和凭据 |
| Management:BusinessServiceName | 管理服务控制的固定本机业务服务 |

新部署先迁移数据库，只在选定首台主机显式初始化；第二台从该主机复制，不在第二台另建空的独立主集群。已有部署更新源码和所需模板，不重新初始化数据库，不删除考试、选择或确认记录。现有 `synchronous_commit=remote_apply` 模板改为 `local`，`synchronous_standby_names` 为空；应用自身连接也强制本机持久提交，复制证据由应用另行核对。

## 持久协调与验证边界

操作意图先落盘再产生外部副作用。同号绑定内容、节点和操作者，冲突拒绝；未决操作阻止新的冲突管理变更。接管中断后从本机原代次确认记录核对真实 WAL 后继时间线及分叉点，不能只凭更大的代次或 LSN 判定恢复正确。证据缺失时保留待核对，不重复提升，不删除工作槽重来。

隔离 PostgreSQL 演练验证实际数据库、WAL、资源、提升和重建；证书装载与 Windows SCM 的合成适配不代表现场断电或网络隔离已验证。最终上线需使用真实节点连接、服务账户和隔离方法演练。单节点期间允许单份数据，补齐前剩余机器再次损坏可能丢失该期间的新数据。
