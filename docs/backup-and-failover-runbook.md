# 备份、恢复与接管

## 单节点运行与启动检查

一个健康活动节点即可运行正式系统。备用未部署、未启动、故障或失联不会单独阻断保存、交卷、回执或其他业务，也无需“单机应急”操作。服务器管理显示当前单份或双份保护状态。

业务启动仍检查数据库、权威节点、服务代次、迁移、资源、证书与解锁材料、答卷和可靠事件。本机关键检查失败时保留恢复态，不能以对端故障为由绕过。既有考试中尚未归档的旧版源材料沿用原兼容规则，不新增清空或重建要求。

初次只部署一台时，使用一节点配置；完成迁移后在首台空主库显式设置 HighAvailability:BootstrapPrimary=true，建立第一代权威身份。已有状态不会被该项改写。第二台须从当前活动节点复制，不在两台各自创建独立主库。首次初始化成功后关闭初始化和自动迁移开关。

## 业务成功的持久边界

数据库业务连接使用 synchronous_commit=local，保留 fsync 和 full_page_writes。成功响应、回执、题包及解锁材料和可靠指令继续经过统一确认服务。确认服务先核对本机权威身份，执行持久 WAL 屏障，核对资源，并将确认记录以 Flush(true) 和持久原子替换保存。本机失败返回可重试错误，客户端保留原请求。

双节点正常时，备机独立核对数据库集群、逻辑身份、代次、状态版本、恢复角色、接收/回放位置、资源和密钥材料，落盘确认；主机取得相同确认后保存双份确认记录。每个备机进程首次执行完整恢复核对，后续保留既有资源版本缓存及变更检查。

对端失败仅使本轮结果按本机确认成功：本机记录明确标记为单节点，不能冒充双份保存。对端确认尝试受短期限限制，连续失联时暂避后后台重试。未完成的本机确认、损坏记录、未持久写入、错误角色或不匹配资源仍阻断成功。

只读观察类目录、设置、名册、试场、监控和报表状态查询保留既有 ReadOnlyObservation 行为；它们不因读取再写一次 WAL。答卷回执、正式报表、下载和解锁等具有确认含义的结果仍受持久确认保护。BatchedBusinessConfirmation 只合并已进入本轮的请求，不能用早于某请求的屏障确认它。单个调用取消不替其他请求撤销确认。

## 主机故障后的方案 A

1. 在现场确认旧主已关机，或已隔离全部业务网络。校园网、虚拟局域网、公网入口等都必须覆盖。记录操作者与原因，并持续保持隔离。
2. 从考务登录页进入“服务器管理 / 故障接管”，连接目标备机的独立管理地址；使用原考务账号登录。正常业务登录可用时继续复用当前会话。
3. 点击页面顶部“接管为主服务器”，确认隔离信息。系统以备机自身独立确认及实际 WAL、资源、密钥和时间线核对可恢复边界，不要求故障旧主日志在线。
4. 系统完成提升、代次递增、旧角色隔离和部署选择，自动启动业务并检查就绪。中断或响应丢失时查询原请求编号，避免重复提升。
5. 学生端在可信拓扑内自动重连，沿用设备身份、参试身份、答案、原请求和提交标识；固定答卷与回执继续保留。
6. 旧主恢复后仍保持业务隔离，通过管理重建从新主生成备库，旧目录保留为隔离原件，禁止回灌新主。追平后自动恢复双节点保护。

本方案没有第三方仲裁和自动隔离设施，不凭心跳丢失自动接管。界面勾选不会替操作者断电或断网；服务代次也不能阻止一台完全隔绝的旧主继续使用旧状态。旧进程发现可信更高代次活动节点后保存失效记录并退出，是额外保护，不能替代现场隔离。

备机只包含已经复制的数据。旧主在复制中断后本机确认的新数据可能缺失，这是已接受的单份运行风险；不能把旧备机证据说成覆盖全部主机历史成功。客户端尽量按原标识补传，不能以新请求重建身份或改写已经固定的答卷。

## 对端恢复

没有角色变化的原备机恢复后自动继续 WAL 复制及版本化资源补齐，后台确认成功后显示双节点保护。恢复不要求考务先点击“恢复保护”。复制槽失效、WAL 已被清理或角色发生变化时，必须用当前活动节点重建，不能让旧数据覆盖新数据。

资源补齐走受信 HTTPS，只允许活动节点向同集群、同代次且仍处于恢复状态的备机写入。快照先进入隔离暂存目录，核对版本后持久替换，保留原资源。重建使用活动节点的基础备份和资源快照，不假设可以访问另一台 Windows 的本地盘符。接收与提升互斥，节点提升后拒绝旧源复制。

## 备份与恢复仍需证明恢复范围

定期备份与主备复制用途不同。备份包含 PostgreSQL 基础备份、适用的 WAL 归档、版本化资源和受保护配置/密钥恢复材料。成功不能只表示创建了目录。备份清单、实际文件校验、隔离暂存和幂等记录继续保留；不会自动覆盖正在使用的数据库目录。

原库仍可读取时，停止业务后比较原库和隔离恢复库的完整业务状态。活动节点、代次必须正确，单节点模式本身不阻断恢复。完整状态相同且本机恢复检查通过后，恢复目标可以按本机确认运行，无需等待备机追平。

原库不可读取时，普通“从历史备份恢复”无法凭备份日期证明包含所有已确认写入。现有 PostgresConfirmedRecoveryEvidence 需要独立最新日志、备节点确认和实际副本一致等证据；缺失时保留 NeedsVerification 与隔离材料，不把未知覆盖范围宣布为成功。这是恢复旧备份的完整性限制，与“另一台缺席就阻断健康主机”不同。完整物理备机接管使用前述方案 A，明确其已复制边界与单份数据风险。

备份恢复不自动替代接管、提升备用库或改变逻辑代次。同一 requestId 的结果继续保存在数据库和管理操作日志中；恢复续行、部署选择、时间线核对与启动门禁保留。新时间线必须通过实际复制协议证明分叉点覆盖原确认，仅较大 LSN 或较大时间线号不构成证据。不要删除确认日志，或用历史备份中的旧日志覆盖最新记录。

## 受保护配置与材料

本机 Confirmation:Directory 必须预建并允许服务账户可靠落盘。双机时配置对端节点标识、HTTPS 地址及至少 32 字符的 PeerToken；HTTPS 证书按正常信任和名称检查，禁止使用考务令牌充当复制凭据。单节点时可以不配置对端地址和凭据，本机资源、证书与数据库配置仍必需。

业务、管理和恢复使用同一套受保护部署选择，保持连接、资源、身份、证书和确认目录一致。时间线证明使用指定 PostgreSQL 工具目录及复制协议账户，秘密只从受保护环境读取。节点私钥与实际连接配置由各自部署，不能放入源码仓库或当作普通资源复制。

运行数据复制、备份与源码同步是不同操作。源码同步排除数据库、真实试题答案、名单、答卷、成绩、日志、备份、归档、私钥、凭据、实际连接配置和所有构建产物。测试材料与联调适配只留在测试目录；两组真实试题目录保持本地。

详细接口及目录约束见[主备管理](high-availability-management.md)，部署参数见[PostgreSQL 部署](../deploy/postgresql/README.md)。现场仍需验证实际 Windows 服务账户、TLS、网络隔离和断电恢复；合成环境通过不能代替现场演练。
