# 备份、恢复与接管边界

当前实现主责为F：F01服务管理与备份恢复、F02主备接管、F04考务管理入口、F05部署运维工具。E01维护隔离测试基础设施，T01/T02由全员执行整体恢复验证；开发期模块故障与恢复测试持续进行。职责与编号见[任务映射](task-map.md)。

## 启动检查

业务服务启动后先进入恢复态。至少核对数据库可读写性、节点角色、服务代次、迁移版本、证书、受保护密钥、已发布题包完整性、未完成命令和定时任务。任何会影响身份、答卷或解锁的检查失败时保持业务写入关闭，管理入口继续可用。

恢复就绪检查除既有项外，还核对**源材料归档**：已发布试卷版本必须有归档行、且归档行结构完整
（长度、摘要长度、逐题摘要非空）。缺失或损坏时保持业务写入关闭，避免接管后无法取回材料继续修题。
该功能上线前发布的考试没有归档行，按「尚未归档」豁免，不会被这项检查拦住。

## 备份与恢复

原库仍可只读访问时，F01 对停止业务后的原库和隔离恢复库做完整业务状态比较，失败则不开放业务。
原库不可读时，备份清单、归档文件存在和固定 WAL 目标均不能证明覆盖最新已确认写入；恢复操作保持
`NeedsVerification`，业务宿主保持停止，同一 `requestId` 可在独立证据补齐后显式重试核对，查询操作不产生副作用。
原始隔离材料和恢复工作副本均须保留。

已确认的 F01/F02 接线边界：原库不可读时，仅 F02 已同步备节点及其**持久确认记录**可作为开放业务的
独立证据来源。F02 必须在对外返回成功前建立可恢复的确认边界，并绑定逻辑服务器、节点、代次、保护模式、
已确认位置、资源与解锁材料版本；核对备节点实际数据库及资源不早于该边界，并证明原主隔离。曾进入
单机应急但备节点缺少随后已确认写入时，不得用备节点旧状态证明完整。F01 只消费经过 F02 核实的结论，
不从备份或历史代次自行推断；独立确认链不可用时，离线原库路径继续拒绝业务启动。

### 当前生产确认与恢复调用链

F01 管理入口的 `ManagementEntryPoint.AddManagementRuntime` 在恢复核对时调用
`PostgresWorkingCopyReadinessProbe`、可选归档重放核对和 `PostgresRecoveryStateComparison`。
后者只读比较停止业务后的原库与恢复库，并要求既有保护模式、活动节点及代次与服务配置一致。
失败时可继续调用 `PostgresConfirmedRecoveryEvidence`，要求受保护本机日志中的最新确认头与
备节点 HTTPS 返回的独立持久确认头完全一致，并核对实际流复制备库、恢复集群/时间线、
全部业务表/列/序列及恢复资源摘要。任一证据缺失时，`ManagementRuntime.RestoreAsync` 持久保存 `NeedsVerification`，
操作查询不重做恢复，新的启动请求由操作门禁拒绝。`RecoveryActivationRunner`、部署切换适配器
和中断后的完成核对均要求通过目标及确认状态检查、且没有其他阻断项。

`PostgresRuntimeRegistration` 在生产环境注册 `PostgresBusinessConfirmation`，HTTP 中间件在
处理器完成后扣住成功内容；二进制题包在结果执行前确认，避免额外复制整包。SignalR 方法结果、
连接补发及后台可靠指令发送分别经过同一确认服务。确认失败返回可重试的 `SERVICE_RECOVERING`，
已持久化的原请求仍由现有幂等存储重放，不能返回未经确认的成功内容或解锁材料。

生产者对权威行执行实际 WAL 写入，在 `synchronous_commit=local` 的事务提交后读取动态 flush LSN，
写入本机待确认头。此设置要求本机 WAL 持久落盘，但不等待配置中的失联同步备库；双机成功仍必须
经过下述独立备机回放及持久确认，不能把本机屏障视为双机确认，也不会自动启用单机应急。
HTTPS 确认请求的整体期限最多为 30 秒，并遵守更短的 HTTP/调用者期限；期限覆盖响应头及完整正文，
防止备机只发响应头后停住而无限占用确认门禁。超时按失败关闭处理，不放出未经确认的成功。
HTTPS 备节点接收器 `PostgresStandbyConfirmation` 独立核对集群、数据库、
节点、代次、保护模式、状态版本、非暂停恢复角色、实际接收落盘及回放位置；同步冲刷并摘要核对
版本化资源，再用本节点实际私钥解密、校验已发布题包。备节点落盘确认后，主节点复核并落盘
同一确认头，最后才能向客户端发送成功。Windows 同目录原子替换使用 write-through，内容先
`Flush(true)`；写入中断留下待确认状态或完整旧头，不能将损坏/不完整 JSON 当作确认。

单机应急只产生本机最新头；缺少应急写入的旧备节点头与它不同，不能证明完整。F01 离线原库
核对还要求原主的**独立日志目录可读**；整机及日志均丢失、目录未保护、记录损坏、备节点不在线、
资源或密钥不完整均保持阻断。不要把确认日志放进历史备份后用旧副本覆盖最新记录。

本改动接通 F01 所需的 F02 持久证据，不表示 F02 全部接管流程完成：既有接管请求去重仍在内存中。
F01 不自动提升备库、改代次、启用应急或重建流复制。恢复选库后的 `/health/ready` 也执行真实确认；
双机部署必须按 PostgreSQL 部署流程让备节点跟随所选恢复主库，未追平时继续拒绝启动成功。
节点/代次改变需独立维护与核对，不能删日志或改 JSON 绕过边界。恢复产生新时间线时，
主侧、备侧及恢复核对器通过真实复制协议读取 `IDENTIFY_SYSTEM` 和 `TIMELINE_HISTORY`，
只有同一集群的祖先分叉点覆盖旧持久确认位置，才能继续确认日志。仅数值更大的 LSN、
检查点中的前一时间线编号或调用者提供的历史文本均不足以授权续接。过早分叉、无关时间线、
工具/权限/历史缺失继续阻断。部署服务账户、证书/ACL、
真实双机网络、断电和 300 人验收另由部署及 T01/T02 验证；合成原生模块测试不替代这些验收。

### 受保护部署配置

主、备业务进程分别设置 `Confirmation:Directory`（预建、仓库外、独立磁盘目录）、
`PrimaryNodeId`/`StandbyNodeId`、主侧 `StandbyHttpsUrl`（有可信证书的 HTTPS 根地址）及
`Backup:VersionedResourcesDirectory`。备机必须运行本业务宿主的确认端点，即使业务授权门禁
处于备节点拒绝写入状态；确认端点独立认证并只读核对 PostgreSQL。
主、备和管理进程的 `Confirmation:PeerToken` 通过受保护配置/环境提供（至少 32 字符）；
不要使用考务令牌、关闭 TLS 校验或写入模板/日志。目标服务器和节点头也必须匹配。
管理进程使用相同本机确认目录、备节点标识/地址，以及受保护的 `ConnectionStrings:ExamStandby`。
数据库账户须能读取完整业务表、序列和 PostgreSQL 控制信息，备机账户还须具备实际包解锁材料。
时间线证明使用 `Backup:PostgresBinDirectory` 内的 PostgreSQL 18 `psql`，目录及程序由部署账户保护，
不从 PATH 搜索，也不允许经过目录联接。可分别在受保护配置设置
`ConnectionStrings:ExamTimeline`、`ExamRecoveryTimeline` 和管理进程的 `ExamStandbyTimeline`，
提供相应端点的复制协议账户；未设置时使用相应数据库连接。账户须有复制协议权限，
代码不会自动授权，也不申请任意服务器文件读取权限。这些连接必须保持相同主机、端口、数据库
和 TLS 模式；口令仅传入子进程环境，不进入命令参数、管理响应或日志。
恢复选择实际切换数据库连接，同时将确认及后续备份绑定到工作副本的 `resources` 目录；
该目录丢失时拒绝继续，不能回退到原资源目录。原库可读但状态不一致或检查权限不足时也保持阻断；
原库连接/读取中断、数据库缺失、服务停止/启动拒绝或 PostgreSQL 明确报告存储 I/O/损坏时，
只能请求独立备节点证据核对，这些错误本身不构成通过。

不带归档目标的基础备份恢复也创建受请求绑定的 `timeline-recovery.json` 及持久刷新后的
`recovery.signal`，由 PostgreSQL 在恢复完成时建立新时间线；启动命令固定禁止继承复制和外部归档命令。
重启沿用已恢复时间线，不重新复制或覆盖故障原件。实际目标检查核对物理清单集群标识，并要求
恢复时间线晚于基础备份源时间线。缺绑定或仍处于旧时间线的旧副本不能认作业务就绪。
升级前须更新预部署恢复 SCM 命令为当前 `BuildServiceCommand` 产生的值；命令不符时保持阻断，
程序不自动修改 SCM。独立日志必须保留；建立新时间线不是删除日志或放宽确认身份的许可。
资源目录须允许相应服务账户读取和持久冲刷；资源复制/发布须先保证两侧版本完整，不能自动跳过
不匹配的资源。缺配置或权限时保持拒绝成功；显式 Development 的内存/空确认不能产生恢复证据。

合成探针测试中的 `Passed` 布尔值仅用于验证编排，不能计作上述生产接线的证据。

可恢复备份必须同时包含 PostgreSQL 基础备份及归档位置、版本化服务器资源、证书和密钥恢复材料、脱敏配置清单和对应提交版本。备份成功不能只表示目录创建成功。恢复在隔离环境进行，恢复完成后重新执行启动检查；关键项失败时禁止开放写入。

同步副本用于单机故障接管，历史备份用于误删除或损坏恢复，两者不能相互替代。正式考试前、考试中和考试后按执行指南建立并验证归档。

仓库实现使用 `pg_basebackup --wal-method=stream --checkpoint=fast` 生成一致基础备份，复制版本化密文资源及受保护配置，并写入不含秘密、带文件长度和 SHA-256 的 `exam-backup.json`。恢复先运行 `pg_verifybackup` 并逐项核对清单，再复制到配置限定的隔离暂存根目录并复核；代码不会自动覆盖当前 PostgreSQL 数据目录。相同 `requestId` 的备份和恢复结果分别写入 `exam.backup_records`、`exam.restore_records`，服务重启后仍可恢复原结果。清单用于发现意外损坏，并非对抗能够同时篡改文件与清单的攻击者；正式部署仍须依靠受限目录 ACL、离线副本及受保护密钥材料。

双机参数、WAL 归档命令、备用库初始化和只读检查脚本见 [PostgreSQL 18 双机部署基线](../deploy/postgresql/README.md)。口令通过 Windows 受保护配置、服务账户环境或 `pgpass.conf` 提供，不能进入脚本参数、日志或仓库。

## 人工接管顺序

1. 确认原主机关机，或已从所有业务网络隔离，并记录操作者、时间和证据。
2. 核对备库仍处于恢复状态、已追平、题包和解锁材料完整、服务证书可用。
3. 提升备库，原子递增 `serverEpoch`，记录新活动节点。
4. 恢复未完成定时和可靠事件，再开放业务写入。
5. 学生端依据稳定 `serverId` 查找可信新主，核对状态后补传进度或原固定答卷。
6. 旧主回归时保持隔离，从新主重新建立为备机；不得让旧数据覆盖新主或形成双写。

无法确认原主已隔离、备库未追平或解锁材料不完整时必须阻止接管。单机应急只能由考务人员明确启用并持续显示风险，不能静默降级。
